# MiniCPM-V 破窗任务：判断与初步方案

> 日期：2026-10-31 | 负责人：黄圣鑫（MiniCPM-V 部分） | 依据：文豪《VB09 穿环打击系统说明》24 页 + 《无人机特警自主打击》466 行 30 天计划 + MiniCPM-V 官方仓库（4.7 版）
>
> 本文回答三件事：**（1）这个任务真正的瓶颈在哪；（2）一周怎么做才不白做；（3）能不能搬到飞机上。**

---

## 0. 一句话结论

**一周内在 GTX 1650 上跑通 MiniCPM-V 4.7-1B、并对"100 m 外红圆"给出检测结果，是能做到的；但"让模型自己看 100 m 的红点"这个做法一定失败——不是模型不行，是光学上那个点只有 3 个像素。**

正确的分工是：

| 谁 | 干什么 | 为什么 |
|---|---|---|
| 传统 CV | 把画面上**所有**红色候选找出来，给坐标（3 px 也够，质心可亚像素） | 不漏；10–60 Hz；不受模型幻觉影响 |
| **MiniCPM-V** | 对着**每个候选的裁剪图**判断"这是不是窗玻璃上的红色标记" | 不错；这正是 VLM 唯一无可替代的能力 |
| Laya / Jev | 吃结构化文本做决策（张光明那半） | 与图像无关，是文本决策引擎 |

这样 MiniCPM-V 在架构里是**必需的**（老师定的路线完整保留），而且它工作的尺度是 100–300 px 的裁剪图，不是 3 px 的原图——**完美绕开 100 m 的死结**。

## 1. 我核对过的证据（不是猜的）

### 1.1 你的机器

| 项 | 实测值 | 影响 |
|---|---|---|
| GPU | **GTX 1650（笔记本）4096 MiB** | 4 GB，是硬天花板 |
| 驱动 / CUDA | 595.79 / CUDA 13.2（驱动侧） | 新驱动，向下兼容 |
| CPU / RAM | Ryzen 7 5800H（8C16T）/ **13.9 GB** | 内存也不宽，别开 32 GB 模型 |

| conda | miniforge3 base + 8 个 env | **不要装进 base**，另建 `mcpv` |
| Turing 架构（sm_75） | 无 Tensor Core、**不支持 bf16**、**不支持 FlashAttention-2** | 官方示例里的 `flash_attention_2`、`bfloat16` 都会踩坑 |

### 1.2 模型（HF `openbmb/MiniCPM-V-4.7-1B`）

| 项 | 值 |
|---|---|
| 权重文件 | `model.safetensors` **3,109,054,480 B ≈ 3.11 GB（bf16）** |
| 实际参数量 | 约 **15.5 亿**（叫 1B，但词表 248094×1024 光 embedding 就占 2.5 亿） |
| 文本骨干 | Qwen3.5 系，24 层，hidden 1024，**混合线性注意力**（3 层 linear + 1 层 full） |
| 视觉塔 | SigLIP2 系，27 层，hidden 1152，**输入 980×980，patch 14**（即 70×70 个 patch） |
| 依赖 | `transformers >= 5.18.0`（当前 PyPI 最新 5.22.1 ✓） |
| 量化版 | int4(bnb) / AWQ / GPTQ / GGUF 都有；Ollama 上 `1b-q4` **1.8 GB** |

**关键的显存算术**：fp16 全量 = 3.11 GB 权重 + CUDA 上下文 ≈ 3.5 GB，而 4 GB 卡开机后可用只有约 3.4 GB ⇒ **大概率 OOM**。
⇒ 必须走 **int4/AWQ（约 1.0–1.5 GB）或 GGUF-Q4（1.8 GB）**，别在 fp16 上浪费时间。

### 1.3 网络（刚实测，VPN 开着）

| 目标 | 结果 |
|---|---|
| huggingface.co | ✓ 200（0.6 s） |
| modelscope.cn | ✓ 200（0.5 s，国内更快，优先用它） |
| pypi.org | ✓ 200 |
| download.pytorch.org | ✓ 200 |
| ollama.com/openbmb/minicpm-v4.7 | ✓ 有 `latest` / `1b` / `1b-q4` / `moe` 四个 tag |

### 1.4 Laya 是什么（顺手看了，免得误期）

Laya 是**纯文本**决策引擎：输入一段文本，输出 `choice / score / noul`（选择题、打分、是/否概率），33 ms。**它不吃图片。** 所以"检测红点"跟 Laya 一点关系都没有，那是张光明负责的"状态→决策"层。你和他之间的接口就是一段 JSON 文本。

## 2. 真正的瓶颈：像素预算（这张表决定一切）

相机是文豪那套 **1080p 双目，标定值 f ≈ 1579 px**（`stereo_calib.yaml`：fx=1579.46, fy=1583.67，1920×1080，水平视场 62.6°）。

成像公式：

```
红点在图上占几个像素 = f × 标记直径 ÷ 距离
（f = 1579 px，无人机相机）
```

目标是"A4 纸内接圆的红圆"，直径约 **0.20 m**：

| 距离 | 占多少像素 | 折算成 ViT patch（14 px 一个） | CV 能不能找 | VLM 能不能"看见" |
|---|---|---|---|---|
| 10 m | 31.6 px | 2.3 个 | ✓ 轻松 | ✓ 能 |
| 20 m | 15.8 px | 1.1 个 | ✓ | 勉强（约 1 patch） |
| **22.6 m** | **14.0 px** | **1.0 个** | ✓ | **临界线** |
| 30 m | 10.5 px | 0.75 个 | ✓ | ✗ |
| 50 m | 6.3 px | 0.45 个 | ✓（要仔细调阈值） | ✗ |
| **100 m** | **3.2 px** | **0.23 个** | ✓（能，但怕压缩） | **✗ 不可能** |
| 200 m | 1.6 px | 0.11 个 | 勉强 | ✗ |

> **100 m 处 1 个像素 = 6.3 cm**。也就是说 3 px 的红点，屏幕上就是一小撮偏红的像素；ViT 的一个 patch 是 14×14 px，红点只占其中一个 patch 的 1/5 —— 模型在编码阶段根本拿不到"这里有个圆"的信息，最多是"这块有点红"。

**这就是为什么"更强的模型"救不了 100 m**。要救只有三条路，且都能算清楚：

| 办法 | 要求 | 代价 |
|---|---|---|
| ① 飞近 | ≤ 22 m 才有 1 个 patch，≤ 10 m 才舒服 | 任务形态变了 |
| ② 换长焦 | 要 f ≥ 7000 px（现相机的 4.4 倍），100 m 才有 14 px | 换镜头/加变焦，最便宜 |
| ③ 放大标记 | 0.20 m → 1.0 m 直径，100 m 就有 15.8 px | 演示用靶标，最省事 |

**给学长拍照时的换算**（手机照片通用）：

```
f_px = 照片宽度像素 × 等效焦距(mm) ÷ 36
红点像素 = f_px × 0.20 ÷ 距离
```

- 手机主摄（等效 26 mm）、4000 px 宽 ⇒ f_px≈2889 ⇒ **100 m 只有 5.8 px**
- 手机 3× 长焦（等效 78 mm）、4000 px 宽 ⇒ f_px≈8667 ⇒ **100 m 有 17.4 px ✓ 能用**
- 手机 5× 长焦 ⇒ 100 m 有 29 px ✓ 很好

⇒ **所以第一件事：问清楚那张 100 m 照片是用哪个镜头、有没有变焦、原图多少像素。** 如果是主摄广角，这张图对 VLM 就是"废片"，只能证明"CV 能找到一个红点"，不能证明"模型看得懂"。

## 3. 架构：三层，各干各的活

```
┌─────────────────────────────────────────────────────────────┐
│ L0 数据：原图，不压缩，保留 EXIF（焦距/机型/时间）            │
└───────────────────────────┬─────────────────────────────────┘
                            ▼
┌─────────────────────────────────────────────────────────────┐
│ L1 传统 CV（10–60 Hz，决定"在哪"）                           │
│   · 红度 R−max(G,B) > 阈值（抗曝光，文豪验证过）             │
│   · 形态学 + 连通域 + 圆度/填充率/尺寸门控                   │
│   · 亚像素质心 + 多帧时序确认（连续 N 帧才算）               │
│   · ★新要求：排除"环框"——环形是空心环，实心圆有洞就否掉     │
│   输出：候选列表 [{u,v,d_px,score}, ...]                     │
└───────────────────────────┬─────────────────────────────────┘
                            ▼ 每个候选裁一张 300×300 的图
┌─────────────────────────────────────────────────────────────┐
│ L2 MiniCPM-V 4.7-1B（0.2–2 Hz，决定"是不是"）                │
│   输入：裁剪图 + 整图缩略 + 一句固定问法                     │
│   输出：JSON {is_marker, on_glass, occluded, note}           │
│   ★不给坐标，只给语义判决（坐标由 L1 保证）                  │
└───────────────────────────┬─────────────────────────────────┘
                            ▼ 结构化文本
┌─────────────────────────────────────────────────────────────┐
│ L3 Laya / Jev（张光明）：文本 → 继续接近 / 人工复核 / 放弃   │
└─────────────────────────────────────────────────────────────┘
```

### 为什么这样分（三条硬理由）

1. **老师定的路线完整保留**：MiniCPM-V 仍在架构里，而且是唯一能做"看懂"的模块；Jev/Laya 的接口也留好了。
2. **CV 负责不漏、VLM 负责不错**：真实楼面上红色干扰极多（红砖、招牌、尾灯、消防栓、红色车）。CV 会把它们全捞出来，VLM 逐个判"这是不是窗玻璃上的标记"——**这正是 1B 模型能干好的活**（输入 100–300 px，红点在里面占 60–200 px）。
3. **能出对照实验**：CV-only / VLM-only / 混合，三列指标一摆，"模型到底带来了什么"就用数据回答了——正好是 30 天文档里要求的"可测收益"，也让老师在后续评审时有据可依。

### 关于"不能再识别穿梭环的圆框"

以前红点是在环内圈里找的（`gate_detector.py` §2.4：看得到环时只在内圈外接框里找），**这是个巨大的拐杖**。现在没有环了，等于要在整张立面里找。所以要加两条：

- **排除环**：连通域内部有洞 / 圆度低 / 环宽比不符 ⇒ 判为环框，不是目标。
- **靠上下文**：候选周围有没有窗框、玻璃反光、墙面 —— 这一条 CV 做不好，交给 VLM。

## 4. 一周计划（每天都有验收标准）

> 前提：**先不要碰无人机、先不要改文豪的代码**。这一周只做笔记本上的离线验证。

| 天 | 做什么 | 命令 / 产出 | 验收标准（怎么判断对不对） |
|---|---|---|---|
| **D1** | 环境体检 + Ollama 保底跑通 | `winget install --id Ollama.Ollama -e`<br>`ollama pull openbmb/minicpm-v4.7:1b-q4`<br>`ollama run openbmb/minicpm-v4.7:1b-q4 "描述这张图 /路径/xx.jpg"` | `ollama ps` 的 PROCESSOR 列显示 **100% GPU**；`nvidia-smi` 显存占用 ≈ 2.0–2.6 GB 且不爆；能正确描述一张普通照片 |
| **D2** | 换成 Python 调用，输出 JSON | 写 `vlm_query.py`（走 `http://127.0.0.1:11434/api/generate`），输入图 + 问题 ⇒ 输出 `{answer, latency_ms}` | 同一张图连跑 5 次，耗时标准差 < 30%；JSON 字段稳定；日志能复盘 |
| **D3** | **Go/No-Go 实验**（最关键） | 合成距离阶梯：拿一张近距清晰红点图，按 f 比例降采样模拟 20/50/100/150 m，逐档问模型 | 得到一张表：**"模型从第几档开始说没有"**。若 100 m 档模型瞎答 ⇒ 架构按第 3 节走，**这就是预期结果，不是失败** |
| **D4** | CV 候选提取 | 复用你已有的 `_归档_20261021\红色目标检测\reddot_detect.py` + `dot_core.py` 的阈值逻辑，改成"输出全部候选" | 在 100 m 图上能把红点框出来（哪怕只有 3 px）；同时输出误检的红砖/招牌数量 |
| **D5** | 拼成混合管线 | `detect.py`：CV 出候选 → 裁剪 → VLM 逐张判 → 画框图 + 输出 JSON | 一条命令跑完一张图，输出：候选数、每个的判定、总耗时；叠加图上框和原图对得上 |
| **D6** | 量化指标 | 20 张图（正样本 + 负样本：故意放红砖/红招牌/无标记） | 误报率、漏报率、P50/P95 耗时，四个数能对上人工标注 |
| **D7** | 交付 | `说明.md` + 一页报告（含 D3 那张距离-成功率表） | 换台机器照 `说明.md` 能复现；报告里每个结论都有数据 |

**风险最大的两天是 D1 和 D5**：

- **D1**：Windows + Turing + `transformers>=5.18` + 混合线性注意力，任何一环卡住都可能耗掉一天。所以 D1 用 Ollama 绕过整条 Python 依赖链（它自带 llama.cpp/引擎，1.8 GB，装完即用）。
- **D5**：裁剪框和原图坐标要对齐（缩放系数算错就全错）。做法：先在一张图上把框画出来给人看，对了再批量。

## 6. 能不能搬到无人机上（提前想，别到现场才发现）

机载算力是 **Khadas + 6 TOPS NPU（RK3588 级）**，不是 GPU。三条独立判断：

### 6.1 算力：能跑，但只能"偶尔看一眼"

- 文本部分（1.55B，int4）在 A76 上大约 **2–6 token/s**，可接受；
- **真正贵的是视觉塔**：SigLIP2 27 层、输入 980×980、默认 9~36 个切片，粗算每张图 **10–30 TFLOP**。RK3588 的 6 TOPS NPU（int8、实际利用率 30–50%）⇒ **单张图 5–20 s**，CPU 更慢。
- ⇒ **机上只能做 0.05–0.1 Hz 的语义确认**，不能做实时检测。实时检测必须留在 CV（CPU 完全够）。

### 6.2 定位：这才是真 P0，而且跟模型无关

- 现在全靠 **VINS（视觉惯性）**，是室内近距离体系；100 m 室外、对着天空/玻璃幕墙，特征少、光照变化大 ⇒ 会漂会丢。
- 要飞 100 m 室外，必须有 **GPS/RTK** 或"人飞到 20–30 m 再交接给视觉"。
- **这一条不在你的任务里，但你要知道它比模型难 10 倍** —— 别让人以为"模型跑通了就能 100 m 破窗"。

### 6.3 光学：换镜头比换模型便宜 100 倍

- 现相机 62.6° 广角，100 m 只有 3 px。
- 换 10–25° 长焦（或加变焦模组），100 m 立刻变成 15–40 px，**问题直接消失**。
- ⇒ 短期最划算的方案不是"更大的模型"，是"更长的镜头"。

### 6.4 现实的分工（建议写进下一阶段方案）

| 端 | 跑什么 | 频率 |
|---|---|---|
| 机上（RK3588） | CV 检测 + 跟踪 + 控制 | 10–30 Hz |
| 地面站（1650 笔记本） | MiniCPM-V 语义判断（走已有的 ZMQ 图传） | 0.2–1 Hz |
| 机上（可选） | 极低频场景描述（GGUF int4，0.05 Hz） | 按需 |
