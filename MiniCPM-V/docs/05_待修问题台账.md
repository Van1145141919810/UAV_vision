### 安全修正：X / L 的可用性（2026-11-24 21:1x）

**先说结论**：在文豪那边，`X`（空中停桨）和 `L`（降落）**任何阶段都有效** ——
`mission.py:200-208` 的 `tick()` 在每个步骤里都会被调用：

```python
if 'x' in flags: request_abort(...)        # FATAL 停桨
if eof:          request_land("stdin EOF") # SSH 断连 → 自动降落
if 'l' in flags: request_land(...)         # 降落（冲刺中推迟到刹停后）
```

**但我们控制台原来有两个“洞”，已经补掉**：

| # | 洞 | 后果 | 修法 | 实测 |
|---|---|---|---|---|
| **A6** | `burst()` 注入时主循环被阻塞 | 注入最长 **7 s** 内按 X/L 传不出去 | 改成**可中断注入**：每 50 ms 查一次键盘，任何键立刻中断 + 0.3 s 松手，再转发该键 | 注入 2 s 的 `w`，第 5 拍按 `x` → **0.51 s 中断**，只发了 4 个 `w`，返回 `('key','x')` |

### 安全修正 2：缓降不再往上拉（2026-11-24 22:0x，**已改 + 离线单测**）

**事故**：21:5x 我做 L 测试（桨拆、飞机在地上）时，`phase_descend` 把设定点拉到 **+0.30 m**，
飞机在地上够不到 → **电机加油门堵转整整 57 秒**（`DESCEND_TIMEOUT`），用户按遥控器急停。
日志证据：`[descend] ZHOLD ramp z: 1.50 → 0.30` 之后连续 57 秒 `target_dz=+0.30 real_dz=+0.00`。

**根因**：`target_z = max(target_z - v*dt, z_target_final)` 会把设定点**往上**夹到 +0.30，
即使飞机已经在目标高度以下。装桨时不会暴露（真能爬到 0.3），桨拆/贴地被挡就一定堵转。

**改法**（`phases.py`，`:180` 附近，+6 行）：

```python
if zf0 is not None and zf0 <= z_target_final + C.DESCEND_REACH_TOL:
    rospy.logwarn("[descend] 实际高度 ... 已不高于降落目标 ... -- 直接进 auto_land（不往上拉）")
    return
```

**离线单测**（机上真 import，不解锁、不发设定点）：

| `zf0` | 结果 |
|---|---|
| 0.00 / 0.10 / 0.49 | **0.000 s 返回**，打印"直接进 auto_land" ✅ |
| 0.51 / 1.50 | **不进守卫**，正常走缓降 ✅（没有误伤） |

判定线 = `DESCEND_Z_TARGET_DZ(0.30) + DESCEND_REACH_TOL(0.20) = 0.50`。

### 安全修正：X / L 任何阶段都有效（2026-11-24 21:5x，**已改代码 + 真机验证**）

**根因**：`phases.py` 里三个循环**完全不读键盘** ——
`phase_takeoff`（起飞那 10 s）、`phase_descend`（缓降全程）、`phase_auto_land`（AUTO.LAND 等待期）。
`request_abort` / `request_land` 只能由读键盘的地方触发，所以那几段时间按 X / L 只是把键堆进 tty 缓冲区。
更糟：`manual()` 一进来就 `keys.drain()`（"丢掉回手动段之前按着的键"）→ **起飞时按的 X 会被丢掉**。

**改法**（`vb09/flight/phases.py`，+61 行，用户 2026-11-24 明确授权）：

1. 新增 `poll_safety_keys(tag)` + 惰性创建的全局 `KeyReader`：
   `X` → `request_abort`；`L` → `request_land`；`EOF`（SSH 断连）→ `request_land`
2. 三个循环各插一次：`if poll_safety_keys("takeoff"/"descend"/"auto_land"): check_abort()`
3. 补 `request_land` 的 import

### E2 语义闸门实测（`window_finder.gate`）

**为什么拖到那时**：真要实现才发现**纯 VLM 闸门无效** —— 4 种问法里最好的也只砍掉 4/10 误报
（明细 `eval/vlm_gate.json`、对照图 `eval/figures/vlm_gate.jpg`）。直接"加个 if"会给人有闸门的错觉。

**判别力其实在物理特征**：目标是「白纸上的红圆」，检测器本来就输出 `nw`
（`detect.py:45-58`，1.3~1.8R 环带 8 扇区里"白"的个数）。

| 闸门方案 | 正例保住 | 负例拒掉 |
|---|---|---|
| 纯 VLM（"圆点还是杂物"） | 5/5 | **4/10** |
| 纯物理 `nw>=4` | 4/5 | 7/10 |
| **物理 + 语义取与** | **4/5** | **9/10** |

**实现**：有红点 → 裁 `6×点径` 小块问 MiniCPM-V（0.2~1.2 s）；
且 `点径≥20 px` 时要求 `nw>=4`；任一不过 → **不删框**，只标 `[!] 红点可疑：<原因>`。

**7 个用例验证**：

| 期望 | 用例 | 点径 | nw | VLM | 通过 |
|---|---|---|---|---|---|
| 正 | 41 m 真点 | 11.9 | 0 | A | ✅ |
| 正 | 22 m 真点 | 17.7 | 8 | A | ✅ |
| 正 | 11 m 真点 | 34.0 | 8 | A | ✅ |
| 负 | win06 花盆 | 11.3 | 3 | **B** | ✅ 拒掉 |
| 负 | win07 花盆 | 16.7 | 0 | **B** | ✅ 拒掉 |
| 负 | test1 红花 | 9.8 | 2 | A | ❌ **漏了** |
| 正 | test2 红圆 | 18.6 | 8 | A | ✅ |

**边界**：41 m 时点只有 12 px，`1.3~1.8R` 白环是**亚像素** → `nw` 恒 0，
所以物理判据只在 `点径 ≥ 20 px` 时启用，否则会误杀真目标。「花丛里的红花」仍会漏。
样本 5 正 / 10 负，阈值还不够硬。
